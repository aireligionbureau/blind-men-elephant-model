# 可重复、可恢复的运行系统

## 目标

运行系统必须把“某次恰好跑通”升级为以下稳定能力：

- 相同输入和配置可以重复执行，不混入旧题材料。
- 进程中断后从最后一个有效检查点继续，不从头重复计费。
- 单个数字人失败只影响该人，不抹掉已经完成的同伴。
- 格式错误先自动修复，临时网络错误退避重试，鉴权错误立即停止。
- 只有通过质量门的结果才标记为成功；确定性保底不能伪装成真实模型判读。
- 系统可以说明停在哪里、为什么停、哪些工作可复用、恢复会调用什么。

## 阶段状态机

每次运行创建 `run_manifest.json`，按以下阶段推进：

1. `preflight`
2. `cohort`
3. `retrieval`
4. `digital_people`
5. `diagnosis`
6. `semantic_verdicts`
7. `shadow_puzzle`
8. `relational_synthesis`
9. `finalize`

阶段状态包括：

- `pending`：尚未开始。
- `running`：当前进程正在处理。
- `succeeded`：本次执行完成并通过校验。
- `reused`：已有制品仍与当前输入吻合，未再次调用模型。
- `recoverable_failed`：当前调用未完成，但检查点完整，可以续跑。
- `failed`：配置、鉴权或输入契约错误，不应盲目重试。

同一运行目录由 `.run.lock` 保证只有一个写入者。进程崩溃留下的锁可以根据进程状态和过期时间自动回收。

## 原子制品

JSON 与 HTML 先写入同目录临时文件，刷新到磁盘后通过 `os.replace` 原子替换。中断只可能留下旧的完整版本或新的完整版本，不会让半截 JSON 覆盖有效结果。

运行清单记录关键制品的：

- 文件名
- 字节数
- SHA-256
- 阶段尝试次数
- 开始和完成时间
- 错误是否可重试
- 阶段质量指标

API key 不进入运行清单、结果文件或报告。

## 逐项检查点

### 检索

每个数字人的检索结果独立写入 `retrieval_items/PERSON_ID.json`，包含：

- 搜索策略
- 候选来源
- 工具调用轨迹
- 来源选择结果
- 证据账本
- 问题、cohort、provider、模型和结果数配置
- 检索实现版本；搜索源、相关性规则或日期策略升级后，旧检查点自动失效

恢复时逐项核验身份和问题上下文。一个文件损坏或某个人检索失败，只重跑该人。三层真实检索要求每个人至少获得外部材料；普通混合检索要求群体外部覆盖率不低于 80%。

无密钥真实搜索的默认顺序是 Google News RSS、Bing RSS、百度网页、Bing 网页和 DuckDuckGo 网页；取得足够相关结果后停止继续请求。单个来源被验证码、超时或结构变化阻断时，会保留失败轨迹并尝试下一来源。泛地点百科、旅游页等只命中一个弱关键词的结果会在进入证据账本前被过滤。数字人仍负责按认知身份证对相关候选作采信、拒绝或忽略，程序不会替它消除这种选择性。

搜索规划显式携带当前日期。国际主题要求至少一次英文查询，中文查询失败时下一次必须换语言、关键词或证据入口。恢复新一轮检索时，阶段进度先按当前有效检查点重算，不继承旧版计数。

### 数字人

每个数字人输出携带由以下内容生成的输入指纹：

- 当前问题
- 完整认知身份证
- 本人的检索材料与证据账本

只有状态成功、完整认知链通过校验、输入指纹一致的输出才会复用。格式错误会把上一次失败原因反馈给模型重写；被截断时只对该人提高输出预算。24人标准版必须 24 条完整链全部通过，系统才进入元模型。

### 语义判决

语义判决按人保存，并对当前判读案例计算输入指纹。旧判决只有在人物、证据、数字人输出和法医诊断都未变化时才能复用。

- `succeeded`：真实模型判读且通过证据锁。
- `no_finding`：当前链条确实没有足够候选形成具体判读，可以保留。
- `fallback`：运行失败后的确定性保底，不允许通过生产质量门。

系统会自动定向重跑 `fallback`，不会重跑已经成功的人。

### 侦探与轮廓

关系综合阶段共有七个可独立恢复的模型检查点：

1. 内容关系提案
2. 阴影关系提案
3. 对抗材料裁决
4. 经典事后复核
5. 候选真相轮廓
6. 最强反轮廓
7. 最终裁决

每次调用完成后立即更新 `contour_candidates.json`。恢复时重新用当前拼图材料验证旧输出；验证通过才复用。侦探的材料裁决和经典复核仍然物理隔离，恢复机制不会改变这一权力边界。

## 自动恢复策略

每个模型调用先执行一次有限重试；少数语义判读未过证据锁时，在同一阶段只定点补齐失败者。默认值是：

- 单次调用额外重试：1次
- 全阶段恢复扫尾：0轮；语义判读允许1次同阶段定点补齐
- 服务自动恢复：同一失败阶段最多1次，且不重置原任务的570秒预算
- 桌面网页默认：`streaming_v2 + optimized_v2`
- 命令行对照基线：`sequential + legacy_sequential`
- 单次新任务分析预算：570秒
- 数字人并发：24
- 语义判读并发：24
- 模型请求并发上限：24，并在限流或暂时性错误时自动降低
- 检索并发：12

错误处理规则：

- HTTP 429、408和5xx：遵守 `Retry-After` 或指数退避。
- 结构校验失败：携带具体校验错误要求模型完全重写。
- 输出截断：在限定上限内提高该阶段输出预算。
- HTTP 400、401、403等配置错误：立即停止，不重复浪费调用。
- 请求超时：标记 `uncertain_remote_completion`，不在同一调用循环里盲目重试。
- 进程退出：下次启动读取清单和检查点继续。
- 用户手动继续或电脑重启后的恢复会获得一个新的、同样受限的恢复窗口；同一新任务内部的自动重试不会刷新预算。

服务进程应在启动时执行：

```powershell
python -m bme_model recover-runs --output-dir runs
```

它只扫描 `initialized`、`running` 和 `recoverable_failed` 的任务；已成功、正在被其他进程处理或明确不可重试的任务不会重复消费。

内置服务已经把这一动作纳入启动流程：

```powershell
python -m bme_model serve --port 8765 --provider three-layer
```

`POST /api/runs` 会先持久化 `queued_job.json` 再进入后台队列，因此即使服务在清单创建前退出，下一次启动仍能找回任务。相同问题、模型和 provider 在已有活动任务时会返回原任务 ID，避免双击或网络重发造成重复计费。页面通过 `GET /api/runs/RUN_ID` 读取真实阶段状态，只在 `quality.json` 通过后开放本次 `report.html`。

启动恢复按任务隔离执行：一个损坏的旧任务会被记录为失败，但不会阻断后续任务恢复。尚未创建运行清单的排队任务会重新走新建入口；已经存在清单的任务才走检查点续跑入口。网页上的数字人数量来自持久化的真实完成进度，不使用计时动画虚构进度；浏览器刷新后会凭任务 ID 继续轮询同一轮运行。

## 最终质量门

`quality.json` 将运行成功与报告“有内容”分开。生产成功至少要求：

- cohort 人数、身份和问题隔离全部有效。
- 检索达到所选证据模式的外部覆盖要求。
- 24个数字人均形成完整认知链。
- 语义判决没有运行性 fallback。
- 侦探层所有必要子阶段完成。
- 轮廓层完成三步对抗流程，或因确实没有建设性关系而作出有依据的保守停止。
- 最终真相轮廓包含对用户原问题的直接回答。

mock、仅模型先验、少量合法 `no_finding` 等情况会作为警告保留，不会被悄悄改名成真实外部证据。

## 能保证与不能保证

系统能够消除大量“不应该存在的卡壳”：半截文件、整轮重跑、单点失败拖垮24人、无意义重复调用、旧结果错配、静默降级和人工寻找修复命令。

系统不能消灭外部世界本身的故障，例如长期断网、余额不足、密钥失效、服务商持续宕机或搜索源封锁。遇到这些情况，正确行为不是伪造一个结果，而是保存全部有效进度、明确标记阻塞原因，并在外部条件恢复后自动续跑。
